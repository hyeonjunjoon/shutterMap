## Problem Statement
카메라/렌즈 실사용 작례를 지도 위에 매핑하고, 같은 데이터를 갤러리(필터 목록)로도 보여주는 서비스. 두 니즈를 묶는다: (1) 장비 구매 전 실사용 샘플을 찾는 니즈(PixelPeeper류), (2) 출사지 발굴 니즈(국내 사진 커뮤니티에 비공식적으로 존재).

## Demand Evidence
없음. 창업자 본인 확인: "증거 없습니다 — 아직 아이디어 단계." 웨이팅리스트, 인터뷰, 확보된 기여자 모두 없음.

## Status Quo
사용자는 지금 쇼핑몰 리뷰/블로그/사진 커뮤니티 게시글을 여러 사이트에 걸쳐 수동으로 뒤져서 해결한다. 장비+장소 두 조건을 동시에 거를 수 있는 단일 창구가 없다는 게 비용이다.

## Target User & Narrowest Wedge
아직 지명할 수 없음. 창업자가 제시한 답은 카테고리("사진 동호회", "장비 덕후")뿐이며, 실명·직함·직접 인용은 없음 — 전형적인 "가상의 사용자" 경고 신호.

**세션 후 보강**: 실제 목적은 포트폴리오 + 본인 사용이므로, 1차 테스트 대상은 외부 낯선 사용자가 아니라 **본인(1) + 지인(2)**으로 이미 확정. 폰 카메라 사진까지 포함하는 것이 명시적 요구사항 — 즉 EXIF가 부실/누락된 스마트폰 사진 경로(PRD 기능 1의 "EXIF 전혀 없는 이미지" 케이스)가 데모 단계에서 실제로 쓰일 핵심 경로다.

## Constraints
- 프리프로덕트, 코드 없음(신규 NestJS/Next.js 스캐폴드만)
- 확정 스택: NestJS(API) + Next.js(UI 전용) + PostgreSQL + 카카오맵 + Cloudflare R2
- PRD v1.0 완성(기능 1~8 전부 명세, 수용 기준 포함)

## Premises
1. 지금 가장 큰 리스크는 기능 목록이 아니라 수요 검증(실제 기여자 확보)이다. — 동의
2. 갤러리/지도는 개인(집 사진) 콘텐츠에 민감한데 신고/모더레이션이 없으니 신뢰 위험이 매몰된다. — 동의
3. 내 사진 수정/삭제 플로우가 명세에 없다 — 출시 전 채워야 한다. — **수정**: 삭제는 셀프서비스로 MVP에 유지, 수정 기능만 MVP에서 제외(삭제 후 재업로드로 대체). (근거: 사용자 0명 단계에서 self-serve 수정까지는 과한 스코프라는 서브에이전트 반박을 일부 수용)
4. 8가지 MVP 기능은 검증 전 기준으로는 범위가 크다 — 증거 확보 전엔 범위를 더 줄여야 할 필요가 있다. — 동의

## Cross-Model Perspective
Codex는 모델 미지원 오류(`gpt-6-astra`가 현 계정에서 미지원)로 실패해 Claude 서브에이전트로 대체 실행함.

- **가장 강한 버전**: 장비(카메라+렌즈+조리개+ISO)로 정확히 태그된 크라우드소싱 샘플 사진 DB — PixelPeeper의 한국 시장 버전. 위치/지도는 장비 검색의 필터 하나일 뿐, 별도 제품이 아니라는 시각.
- **핵심 인사이트**: "실명을 대지 못하고 카테고리로만 답했다"는 게 가장 많은 걸 드러낸다 — 8개 기능, 지도, 공개범위, 갤러리 전부가 상상한 페르소나를 위한 설계였다는 뜻.
- **반박한 전제**: 전제 3(수정/삭제 공백). 사용자 0명에서는 DB 수동 처리로 충분하며, self-serve 플로우는 아직 존재하지 않는 문제에 스코프를 쓰는 것. 반증 증거: 첫 10~20명 기여자 중 수정/삭제 요청이 월 5분 이하 처리량이면 전제는 틀렸던 것.
- **48시간 프로토타입 제안**: Next.js만(NestJS 생략) + Supabase(Auth+DB+Storage) + 클라이언트 `exifr`, 업로드+갤러리 그리드(드롭다운 필터)만, magic-link 이메일만. 지도/카카오/공개범위 3단계/좋아요/상세페이지는 전부 생략하고 실명 5명에게 직접 배포.

## Approaches Considered
### Approach A: 최소 검증 프로토타입 (Lean Validation)
Next.js + Supabase, 카카오맵/NestJS 생략. 업로드+EXIF+갤러리(필터)만. Effort S, Risk Low. 실패 비용이 작지만 지도·위치축은 검증하지 못하고 PRD 확정 스택과 다른 임시 스택.

### Approach B: 현재 PRD 그대로 전체 구현 (Ideal Architecture)
NestJS+Next.js+PostgreSQL+카카오맵+R2로 8개 기능 모두 구현. Effort XL, Risk High. 장기 아키텍처 재작업이 없지만, 수요 0 상태에서 가장 큰 투자를 가장 위험한 가정(누군가 쓴다) 위에 건다.

### Approach C: 코드 없는 수요 테스트 (No-Code Demand Test)
구글폼/노션 수동 제출 + 구글마이맵 수동 핀. Effort S, Risk Low. 코드 투자 0으로 지도+갤러리 두 축 동시 테스트 가능하지만 자동화가 전혀 없음.

## Recommended Approach
세션 중 권장안은 C → 신호 확인 후 A였으나, **사용자가 명시적으로 Approach B(현재 PRD 그대로 전체 구현)를 선택**했다. 선택 근거(세션 후 확인): 이 프로젝트는 불특정 외부 수요를 노리는 스타트업이 아니라 **포트폴리오용 설계 + 본인이 직접 쓸 서비스**다. 따라서 Phase 2A의 "낯선 사람에게 수요 증명" 프레이밍은 이 프로젝트의 실제 목적과 어긋나며, B(전체 기능 구현)가 포트폴리오로서의 완성도와 본인 사용성 모두에 더 맞는 선택이다.

## Open Questions
- 기능 1~8 범위를 줄일지 여부 — 전제 4에는 동의했으나 B를 선택하며 실제 축소는 하지 않음
- 수익구조(제휴 등)는 MVP에서 구현하지 않되, 갤러리 구조만 나중에 끼우기 쉽게 열어둠 — 실제 숫자 검증은 미착수

## Post-Session Addenda (오피스아워 종료 후 보강)

**신고/모더레이션(전제 2) 해결**: 기능 9(사진 신고 및 운영자 조치)로 PRD에 추가. 신고 사유 분류 + 운영자 수동 검토 + 비공개/삭제. 정보통신망법상 임시조치 근거 마련 목적도 겸함.

**콜드스타트 재평가**: 애초에 "낯선 다수에게 수요를 입증해야 한다"는 Startup-mode 프레이밍이 이 프로젝트의 실제 성격과 맞지 않았다. 실제 사용 경로는 본인+지인+카메라 커뮤니티 간단 공유로 이미 확정되어 있어, 공급자가 누군지 모르는 전형적인 양면 시장 콜드스타트 문제는 해당하지 않는다. 남은 건 사업성 질문이 아니라 UX 디테일: 소규모 공급(본인+지인)에서는 장비+지역 필터 조합 다수가 0건 결과가 될 수 있으므로, 지도/갤러리에 빈 결과 안내 문구를 추가함(기능 4, 8 수용 기준에 반영).

**최종 입장**: 이 프로젝트는 "검증 전 스타트업"이 아니라 "포트폴리오 + 본인/지인 사용 + 소규모 커뮤니티 공유"로 성격이 재확정됨. Phase 2A의 수요 검증 질문(Q1-Q3)은 참고 정보로만 남기고, 향후 범위를 실제 스타트업으로 전환할 신호(예: 커뮤니티 공유 후 낯선 사용자의 자발적 업로드)가 나타나면 그때 재검토.

## Success Criteria
- PRD v1.0의 각 기능별 수용 기준(Given/When/Then)을 모두 통과
- 최소 1명의 실제 기여자가 가이드 없이 사진을 업로드하고 지도/갤러리에 노출되는 것을 확인

## Dependencies
- PRD.md (`shutter-map/docs/PRD.md`) — 이미 확정된 범위/스택의 소스
- 카카오맵 JS SDK, 카카오 로컬 API, 카카오/구글 OAuth 앱 등록 필요
- Cloudflare R2 버킷 설정 필요

## The Assignment
포트폴리오/본인 사용 목적이므로 수요 검증형 과제 대신 **엔드투엔드 검증형 과제**로 재정의: 본인 사진(DSLR/미러리스 등 EXIF 풍부) + 지인 2명의 사진(최소 1명은 스마트폰 사진 포함) 총 3인분을 실제로 업로드해보고, 기능 1의 세 가지 EXIF 케이스(완전/부분/전무)가 각각 미리보기에서 올바르게 동작하는지, 기능 2(수동 위치 등록 강제)와 기능 3(공개범위 기본값 fuzzy)이 실제로 막힘없이 끝까지 통과하는지 확인한다.

## What I noticed about how you think
- "증거 없습니다 — 아직 아이디어 단계"라고 솔직하게 답했다. 많은 창업자가 여기서 애매한 말로 포장하는데, 숨기지 않았다.
- 서브에이전트가 Approach C(코드 없는 검증)를 추천했는데도, 명시적으로 B(전체 PRD 구현)를 선택했다 — 추천을 그대로 따르지 않고 자기 판단으로 결정했다.
- PRD 자체에 EXIF 특이사항(렌즈 코드값, X100VI 같은 고정렌즈 카메라, ILCE-7M4 표기 문제)까지 이미 파고들어 적어뒀다 — 도메인을 깊게 알고 있다는 신호다.
- 전제 3을 통째로 받거나 버리지 않고 "삭제는 유지, 수정만 제외"로 정교하게 쪼개서 답했다 — 디테일에 대한 taste를 보여준다.
